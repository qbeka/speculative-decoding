    Details
    
      
    A small model drafts a few tokens. One pass of the large model checks them together, keeps them up to the first rejection and writes the next token itself. A controller picks how long the next draft should be.
    
      
    The engine is exact, which means it has the same output distribution as the large model alone. The controller was the part under test, and it lost that test.
    

      
    Results
    
      
    
        
    Fastest decoder
    2.27x the large model aloneMeasured on held-out receipts with a 95% CI of 2.05 to 2.55, across 2,754 timed requests. This came from a fixed length with a distilled draft, which is larger than the draft in the replay, and the controller played no part in it.
    
        
    Controller, preregistered test
    Failed, 0.92x a tuned fixed lengthAdaptive had to beat fixed length 12 on held-out receipts, and it came in below it with a 95% CI of 0.866 to 0.968.

    Limits
    
      
      
        
    • Exact means the same output distribution. Each run's text differs, and task accuracy did not change. The replay does not show that any two outputs match.
      • 
        
    • The controller limits the damage from wrong tuning, and a short fixed length on the stock draft avoided the same problem without it.
      • 
        
    • A seed bug in my harness made requests dependent, so I discarded a 2.8 hour final run and reran the frozen plan. The discarded run put the primary ratio at 1.04x, so the size of the loss is not settled.
      • 
        
    • The batching is static and ran on one laptop, so these numbers say nothing about production serving.
      • 
        
    • The replay shows saved timings and text from single requests. The recordings are the ones whose draft length changed most, so their rates can differ from the results above, which cover the whole run.
      • 
      
    

      
    Method
    
      
    The plan was frozen before the test split ran. The report has every comparison and how it was run.
